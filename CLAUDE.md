# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Datum is an SEO content pipeline built on Payload CMS. It has two npm workspaces:

- **`cms/`** — Payload CMS 3 app (Next.js 16 + Postgres) that stores `templates` and `articles` and serves the admin panel.
- **`pipeline/`** — a standalone Node/TypeScript CLI that drives articles through the content pipeline (research → generate → QA → information gain) by calling Payload's local API directly against `cms/src/payload.config.ts`. It is not an HTTP client of the CMS; it imports Payload in-process (see `pipeline/src/payloadClient.ts`), so `cms` and `pipeline` share one Postgres database and one set of generated types (`cms/src/payload-types.ts`).

Root `package.json` scripts just delegate into the workspaces (`npm run dev`, `npm run seed`, `npm run pipeline:fetch|run|report`).

## Commands

Install once from the repo root: `npm install` (npm workspaces; installs both `cms` and `pipeline`).

Database: `docker-compose up -d` starts Postgres (`datum`/`datum`/`datum` on 5432). Copy `.env.example` to `.env` at the repo root (and `cms/.env.example` to `cms/.env`) before running anything — `pipeline/src/config.ts` loads `cms/.env` first, then root `.env`, and real environment variables always win over both files.

Adding a Payload `select` field creates a new Postgres enum. On the next `npm run dev`, drizzle's dev push detects this and interactively asks "Is enum … created or renamed?" — run `dev` in a real terminal (not backgrounded/piped) and choose "create enum". Until that pending schema change is resolved, `npm run test:int`'s `api.int.spec.ts` doesn't fail, it hangs — `payload.config.ts` leaves dev push on for *every* process that calls `getPayload`, so the vitest worker runs drizzle's push itself and its prompt has no TTY to answer it. Resolve it by running `npm run dev` once in a real terminal first; don't go hunting for a dev server, there may not be one.

Worktrees share the single `datum` dev database by default (same `DATABASE_URL` unless overridden), so a branch with schema changes can be asked to drop another branch's tables on push — decline that prompt. Instead, point that worktree's gitignored `.env`/`cms/.env` `DATABASE_URL` at a per-worktree database, e.g. `createdb -O datum datum_<branch>`, then `npm run seed`.

**CMS** (`cms/`, or `npm run <script> --workspace cms` from root):
- `npm run dev` — Next dev server at `http://localhost:3000`
- `npm run seed` — upserts the three content templates (Listicle, How-To, Comparison) and a dev admin user (`admin@datum.local`, password from `SEED_ADMIN_PASSWORD` or `datum-dev-password`). Add `-- --with-brand-voice` to also upsert and activate the demo brand voice (`cms/src/lib/brandVoiceFixture.ts`); the default seed deliberately leaves no brand voice so the admin's onboarding empty state stays reachable.
- `npm run generate:types` — regenerate `src/payload-types.ts` after changing a collection; both `cms` and `pipeline` import types from this file, so run it after any collection schema change
- `npm run lint` / `npm run typecheck`
- `npm run test:int` — Vitest integration tests (`tests/int/**/*.int.spec.ts`)
- `npm run test:e2e` — Playwright e2e tests (`tests/e2e/`); if no server is already running at `localhost:3000`, Playwright starts one itself by running `pnpm dev` (hardcoded in `playwright.config.ts`'s `webServer.command`), so either have `pnpm` installed or start `npm run dev` yourself first
- `npm test` — runs both test suites in sequence

**Pipeline** (`pipeline/`, or `npm run pipeline:<cmd>` from root):
- `npm run fetch -- --template <name-or-id> --count N` (or `npm run pipeline:fetch -- …`) — pull content-gap keywords from Ahrefs and create up to N new `topic_selected` articles, each already carrying that template. `--template` is **required**; `--count` defaults to 5. Keywords that already have an article are skipped, so a second fetch against the same mock keyword set creates nothing.
- `npm run run` (`pipeline:run`) — advance every article that has a `template` assigned through research → generate → QA → informationGain, one stage at a time across all eligible articles
- `npm run report -- --period week|month` (`pipeline:report`) — print QA pass rates, spend, and a failure digest
- `npx tsx scripts/assign-template.ts <articleId> <templateName>` — tags an existing `topic_selected` article with a template. `fetch` now assigns one at creation, so this is for articles created another way (or re-templated); the admin's Assign template action (`assignTemplateAction`) does the same thing from the ops UI
- `./scripts/ig-e2e.sh` (from the repo root: `pipeline/scripts/ig-e2e.sh`) — the mock-mode information-gain walkthrough: seed → fetch → assign template → run all four stages → assert on status, the `information-gain-runs` row and the cost rows → re-run to prove it's a no-op → report. Exits non-zero on any failed assertion, refuses to run under `MOCK_MODE=false`, and is repeatable against a database that has already been walked through. Its Payload-side helper is `scripts/ig-e2e-probe.ts`
- `npm run typecheck`
- `npm test` — Node's built-in test runner (`tsx --test test/*.test.ts`); to run a single file: `npx tsx --test test/structuralChecks.test.ts` (`npx` is required — `tsx` is only on PATH inside npm scripts, not in an interactive shell, unless it's installed globally)

Both workspaces resolve `cms/src/payload.config.ts` at runtime, so pipeline commands need the same env vars as the CMS (`DATABASE_URL`, `PAYLOAD_SECRET`) in addition to pipeline-specific ones.

## Environment / mock mode

`MOCK_MODE` (see root `.env.example`) governs whether the pipeline hits real paid APIs:
- `MOCK_MODE=true` (or unset with no `ANTHROPIC_API_KEY`) — `pipeline/src/llm.ts` returns canned fixtures from `pipeline/src/fixtures.ts` instead of calling Claude, and `pipeline/src/ahrefs.ts` uses `MockAhrefsClient` instead of the real Ahrefs API. This is the default for local dev and lets `pipeline:fetch`/`pipeline:run` work with zero API keys. Stages with more than one call shape select a sub-fixture by `fixtureKey`: `claimExtraction` has `page` (one per SERP page and per internal article), `facets` (the single clustering call per snapshot), and `draft` (the informationGain stage's decomposition). `mockFixture` **throws** on a key it doesn't know rather than falling back to the whole entry, and `fixtureKey` survives `llm.ts`'s per-call live/mock decision — a `claimExtraction` request that lost its key would otherwise receive an object of three fixtures where a claim list was expected.
- `MOCK_MODE=false` requires a key for every configured model's provider — `ANTHROPIC_API_KEY` for `claude-*` ids, `OPENAI_API_KEY` for `gpt-*`/`o3`/`o4-mini` ids (`providerForModel` in `cms/src/lib/llmProvider.ts` decides by prefix; there is no separate provider flag). `AHREFS_API_KEY` additionally requires `TARGET_DOMAIN` and `COMPETITOR_DOMAINS` to be set (see `pipeline/src/config.ts` for the exact validation). Note `MOCK_MODE=true` mocks Ahrefs too, so an Ahrefs key is inert until the LLM side is also live.
- `pipeline/src/llm.ts` has one call path per provider (Anthropic Messages API; OpenAI Responses API with `json_object` output and the `web_search` tool for `factCheck`); both return the same `LlmResult` so stages and cost logging are provider-agnostic.
- The CMS makes one LLM call of its own — brand-guide extraction (`cms/src/lib/brandVoiceExtract.ts`) — and follows the same rule via `extractionMockMode()`: `MOCK_MODE` wins when set, otherwise it mocks whenever `ANTHROPIC_API_KEY` is unset (returning the demo fixture) and never throws for a missing key. Its model is `BRAND_VOICE_EXTRACT_MODEL` (default `claude-opus-5`). Next only loads `cms/.env`, not the root `.env`, so set these in `cms/.env` for the admin.

Which model runs each LLM call is an admin setting: the **Models** global (`llm-settings`, `cms/src/globals/LlmSettings.ts`, linked under Governance) has one dropdown per stage plus one for brand-voice extraction. Resolution order (`cms/src/lib/llmSettings.ts`, shared by both workspaces): admin choice → env override (`PIPELINE_MODEL_GENERATE` / `PIPELINE_MODEL_FACT_CHECK` / `PIPELINE_MODEL_QUALITATIVE_REVIEW` / `BRAND_VOICE_EXTRACT_MODEL`) → `claude-opus-5`. The pipeline resolves this once per run in `pipeline/src/models.ts` (which is also where the per-model API-key check happens, since the DB has a say) and carries it as `StageContext.models`; mixing providers per stage is fine. The dropdown's choices and their prices come from one place, `cms/src/lib/llmCatalog.ts` (Claude 5 family + OpenAI's flagship models) — add a model there, not to `pricing.ts`, which derives from it. An id outside the catalog (via env) still runs but logs cost as $0 with a console warning, which silently breaks the spend reporting.

## Pipeline architecture

An article moves through a fixed status state machine, driven entirely by `status` — not by any queue or scheduler:

```
topic_selected → researched → drafted → qa_passed → verified → approved → published
                                  │          │
                          QA fail ↓          ↓ REVISE / HUMAN_REVIEW / BLOCK
                           needs_revision    needs_review / blocked

Reviewer moves out of a held state (none of these is something pipeline:run does):
  needs_review | blocked  --override, fresh justification-->  verified
  needs_review | blocked  --send back-->                      needs_revision
  needs_revision          --regenerate-->                     researched   (re-enters generate)
```

`pipeline/src/stages.ts` defines `stages: Stage[] = [researchStage, generateStage, qaStage, informationGainStage]`. `runPipeline()` walks that array in order; for each stage it queries Payload for every article whose `status` equals the stage's `entryStatus` and has a `template` assigned, runs the stage, and writes back `status` + the stage's output data. This makes reruns idempotent/convergent for the statuses that have a stage: an article only advances once per run through each stage it's currently eligible for, and a fresh `pipeline:run` naturally picks up wherever those articles are stuck. A stage can also report work that failed *without* changing the article's outcome through `StageOutcome.warnings` (the informationGain stage's candidate-domain write is the one user): `runPipeline` logs each as `[<stage>] article <id> warning: <message>`, counts it as `warned` rather than `failed`, and stores it on the article's audit row — visible, but no retry and no effect on the exit code. A throw inside one article's stage run is caught, logged as `[<stage>] article <id> failed: <message>`, and counted in a per-stage summary line; that article keeps its status (so the next run retries it) and the rest of the batch — and every later stage — still runs. Caught is not swallowed: `runPipeline` returns a `PipelineRunSummary` (`{ stages: [{ stage, total, failed }], failed }`) and `pipeline/src/index.ts` prints the per-stage counts and exits **non-zero** when anything failed, so a scheduled run's alerting and retry policy still see stuck articles.

**`needs_revision`, `needs_review` and `blocked` are dead ends for `pipeline:run`**: no stage's `entryStatus` is any of them, so the pipeline never picks those articles back up on its own. A human decides what happens next, through one of the reviewer actions in `cms/src/components/ops/actions.ts`:

- **Regenerate** (`regenerateArticleAction`) sends the article back to **`researched`**, the `generate` stage's entry status, with `revisionNotes` built from the latest `information-gain-runs` row's `reasons` (one `- [CODE] message` line each, falling back to the QA failure lines when there is no run), `revisionCount` incremented, and `qaResults`/`informationGain` nulled. The next run rewrites the draft with those notes rendered verbatim into the prompt, then re-runs QA and scoring **against the same corpus snapshot**, which is what makes the second scorecard comparable to the first. This is the regeneration loop, and it is the only way back into the pipeline that carries the reasons with it. Note where the control lives: `ArticleReview.tsx` offers Regenerate on **`needs_revision` only**, so regenerating a `needs_review`/`blocked` article is a two-step move — **Send back** first, then Regenerate. The server action itself has no such restriction, and run rows are immutable, so the blocking run's reasons are still found after Send back has nulled the article's `informationGain` summary.
- **Reset to drafted** / **Send back** put the article at `drafted` / `needs_revision` respectively, re-entering (or waiting for) the `qa` stage without regenerating.
- **Override** (`overrideReviewAction`) moves a `needs_review`/`blocked` article straight to `verified` on the reviewer's judgement.

Two `beforeChange` hooks on `Articles` (`cms/src/lib/articleReviewGate.ts`) make those the *only* routes, for REST and admin edits as much as for the ops UI. `gateVerifiedStatus` refuses `status: 'verified'` unless the write carries an `informationGain.decision` of `PASS` or is a justified override. `gateReviewOverride` intercepts every transition *out of* `needs_review`/`blocked`: backward targets (`needs_revision`, `drafted`, `researched`, `topic_selected`, and the review statuses themselves) pass through, and everything else demands a `reviewJustification` **different from the persisted one** — the admin submits the whole document, so a stale justification would otherwise ride along and satisfy the gate with nobody typing. It also overwrites `reviewedBy` with the acting user and records the override in the audit log. That freshness rule is why the informationGain stage writes `reviewJustification: null` whenever it lands on `needs_review` or `blocked`. The ungated list is deliberately an allow-list of *backward* targets, so a newly added status defaults to gated rather than to an unnoticed detour out of review.

- **research** (`pipeline/src/research.ts`) — Ahrefs SERP research for the article's keyword, plus the information-gain baseline: it fetches the top-ranking pages, extracts claims from them via `claimExtraction` LLM calls, clusters those claims (pooled with claims from our own related published articles) into consensus facets and gaps, and writes `research.snapshot`/`research.queryCluster`/`research.facets`/`research.gaps` onto the article. The underlying corpus snapshot is reused across articles on the same keyword for up to 14 days rather than rebuilt on every run — but only when it has a baseline: a snapshot whose crawl failed *or* whose extraction produced no claims is stored `empty` and never reused. The crawler follows redirects itself and refuses any hop that resolves to a loopback, private, link-local, or otherwise non-public address (`pipeline/src/corpus/addressGuard.ts`). See `docs/information-gain.md` for the fetch limits, what the crawler refuses, the reuse rule, and claim/facet shapes.
- **generate** (`pipeline/src/generate.ts`, prompts in `pipeline/src/generatePrompt.ts`) — one LLM call that returns a JSON object (title, slug, SEO fields, FAQ items, markdown body) built from the assigned `template`'s outline/dos/donts/SEO spec plus the research data; markdown is converted to Payload's Lexical rich text via `pipeline/src/richtext.ts`. The system prompt is the platform style guide plus, when a brand voice is active, the `# Brand voice (tenant)` block; the tenant's writing samples go in the user prompt as few-shot examples.
- **qa** (`pipeline/src/qa/index.ts`) — three independent checks that must all pass to reach `qa_passed`, else the article goes to `needs_revision`:
  1. `runStructuralChecks` (`pipeline/src/qa/structuralChecks.ts`) — pure, deterministic, zero-LLM: title/meta length limits from the template's `seoSpec`, heading structure (exactly one H1 via the title, no skipped levels, required H2 sections present), FAQ count range, OG tag presence, Flesch-Kincaid reading grade ≤ 11, and banned-phrase scanning of body/title/titleTag/metaDescription/ogTitle/ogDescription/faqItems against `docs/style-guide.md` (`source: 'platform'`) plus the active brand voice's `bannedWords` (`source: 'brand'`).
  2. `factCheck` — LLM call with the web-search tool enabled (`needWebSearch: true` in `llm.ts`).
  3. `qualitativeReview` — LLM call judging style-guide and template dos/don'ts adherence. With an active brand voice it also returns `voiceScore` (1–5, informational only), `voiceNotes`, and `notTraitViolations` (clear breaches of a "what we are NOT" trait, each with a verbatim excerpt); `decideQualitative()` in `pipeline/src/qa/verdicts.ts` fails the check only on `passed: false` or a non-empty `notTraitViolations`.

- **informationGain** (`pipeline/src/informationGain/index.ts`) — `qa_passed` → `verified` / `needs_revision` / `needs_review` / `blocked`. Extracts the draft's own claims (`claimExtraction`, `fixtureKey: 'draft'`), judges each against the research stage's corpus snapshot in per-facet batches (`informationGainJudge`), hunts web-search evidence for the materially novel checkable ones (`evidenceVerification`), and hands the resulting `Scorecard` to `decidePolicy` — the only place the verdict is made. Thresholds (the `information-gain-policy` global → `INFORMATION_GAIN_*` env → default) and the `evidence-sources` domain table are resolved **once per run** into `StageContext.policy`/`evidenceSources`, so every article in a run is judged identically; the resolved policy is hashed into a `policyVersion` stamped on every result. Writes one immutable `information-gain-runs` row (full scorecard, every claim, its evidence) plus a summary on `Article.informationGain`. Orchestration only — every pure rule lives in `pipeline/src/informationGain/scorecard.ts`. See `docs/information-gain.md`.

**Brand voice** (`cms/src/lib/brandVoice.ts`) is the tenant-level governance layer on top of the style guide. `pipeline/src/brandVoice.ts` loads the single `active` `brand-voices` record into `StageContext.brandVoice` (normalised to `BrandVoiceContent`, or `null`); every consumer must handle `null` — with no active voice the pipeline behaves exactly as before. The helpers in `cms/src/lib/brandVoice.ts` (`brandVoiceToPrompt`, `brandVoiceSamplesToPrompt`, `bannedWordsOf`, `brandVoiceToGuideMarkdown`, `brandVoiceActivationProblems`, `parseBrandVoiceContent`) are pure and imported by both workspaces, so keep that file free of `next`/`react`/`payload` runtime imports and `@/` aliases.

`fetchTopics()` (`pipeline/src/fetchTopics.ts`) is the entry point that creates new `topic_selected` articles: it pulls Ahrefs content-gap keywords (competitor terms the target domain doesn't rank for), scores them by `volume / difficulty`, and creates the top N — skipping keywords that already have an article.

Runs are started from the admin in two different ways, and the difference matters: **Start run** on the article board (`runSelectedArticlesAction` → a `selected` pipeline run) advances the articles a person ticked and creates nothing, while **Discover and run** on `/admin/ops/topics` (`startContentRunAction` → an `admin` run) calls `fetchTopics` first and only runs what it just bought. `contentRun.ts` branches on `PipelineRun.source` for exactly this. A run's outcome is reported honestly: `runPipeline` swallows a single article's failure so the batch survives, so `executeContentRun` reads `result.failed` and marks the run **`failed`** when nothing advanced, storing each `StageFailure` (article, keyword, stage, message) on the run row's `warnings`. A `GlobalRunBar`, mounted from `admin.components.providers` so it wraps every admin route, polls `latestRunAction` and reports live progress — per-article stage, elapsed time, a progress bar derived from article status via `STAGE_PROGRESS` — then lingers 30s after completion, timed from `completedAt` rather than page load. It is the **only** poller: the board's `RunStatusPanel` renders server props and the bar calls `router.refresh()` once when a run settles. The panel shows what moved and what did not — without it a caught stage failure was visible only in the server log. A `selected` run carries its article ids on the run row from the moment it is created.

Every article needs a `template` before `runPipeline` will touch it. `fetch --template` assigns one at creation; `scripts/assign-template.ts` and the ops UI's Assign template action cover articles created another way. Nothing *picks* a template for you — that judgement stays human.

## Cost tracking

Every LLM call must go through `completeJSONLogged()` in `pipeline/src/llm.ts` — it wraps `completeJSON()` and writes one `cost-log` row (tokens, provider, model, computed `costUsd`) per call, keyed by `pipelineRunId` and `article`. The research stage's `claimExtraction` calls (one per fetched baseline page plus one for facet clustering, only when a new corpus snapshot is built — reuse costs $0) are logged the same way, so a snapshot build shows up in spend reports as ordinary `claimExtraction` rows against that article. One gap: if the model's reply isn't valid JSON, `parseJsonReply` throws inside `completeJSON()` before the row is written, so that call's (paid) tokens go unrecorded and spend reports undercount. Stages should never call `completeJSON()` directly for anything that should be cost-tracked. `qaStage` sums that article's `cost-log` rows into `totalCostUsd` after its own LLM calls, so it always includes the current run's `factCheck`/`qualitativeReview` cost. The `informationGain` stage does the same twice: once filtered to this `pipelineRunId` and the three claim-level stages (`claimExtraction`, `informationGainJudge`, `evidenceVerification`) for the run row's own `costUsd`, then unfiltered for the article's `totalCostUsd`. Note the first sum is by *stage name*, and the research stage's snapshot-build extractions are `claimExtraction` rows under the same run id — so when a snapshot is built in the same run that scores the draft, the build's cost lands on the scoring run row too (see `docs/information-gain.md`'s Cost section). `pipeline/src/report.ts` reads `cost-log` for spend-by-stage/spend-by-model and a "cost per published article" / "waste on unpublished articles" breakdown. Prices live in `cms/src/lib/pricing.ts` (re-exported by `pipeline/src/pricing.ts`) because the CMS-side brand-guide extraction logs cost too: `logExtractionCost()` writes a `stage: 'brandVoiceExtract'` row with no `article` and a `pipelineRunId` of `brand-voice-extract:<uuid>`.

## Rich text conversion

Payload stores article/template body content as Lexical JSON. `pipeline/src/richtext.ts` and `cms/src/seed.ts` both hand-build/walk that JSON shape directly (no Lexical runtime dependency) — `lexicalToMarkdown`/`markdownToLexical`/`lexicalToPlainText`/`extractHeadings` convert between it and plain markdown/text for LLM prompts and structural QA. When adding new node types to article bodies, both `richtext.ts` (pipeline) and any seed helpers (cms) need matching node builders.

## Style guide as data

`docs/style-guide.md` is not just documentation — `pipeline/src/styleGuide.ts` parses its `## Banned phrases` section into a `bannedPhrases: string[]` array at runtime, which both the `generate` LLM prompt (as instructions) and `runStructuralChecks`'s `BANNED_PHRASE` check (as a regex scan) consume. Keep new banned phrases under that exact heading, one per bullet, in the format `phrase (optional parenthetical note)` — the parenthetical is stripped before matching. The style guide is the *platform* baseline; a tenant's brand voice (see Pipeline architecture) layers on top of it rather than replacing it — tenant banned words are appended to the scan, and the voice prose is a separate, labelled prompt section.

## CMS collections (`cms/src/collections/`)

- **`Templates`** — content templates (`Listicle`, `How-To`, `Comparison` are seeded, and `createTemplateAction` adds more from `/admin/ops/templates`; a created one starts with the seeded SEO limits but **no** `requiredSections`, since every heading there is enforced against the draft); holds the outline (rich text), dos/don'ts arrays, `requiredSections` (H2s enforced by structural QA — the outline itself is prose guidance, not enforced directly), and `seoSpec`.
- **`Articles`** — one row per article; `status` drives the pipeline; `research`, `qaResults`, `qaModels`, `generationModel`, `totalCostUsd` are pipeline-written fields — by convention only, as the collection doesn't mark them `admin.readOnly` or restrict access, so the admin UI will happily let a human overwrite them (and the next `pipeline:run` may overwrite them back). `revisionNotes` and `revisionCount` track a manual send-back-for-revision loop: `revisionNotes` is rendered into the generate prompt verbatim (see `docs/information-gain.md`'s Gap-fed generation section) so a re-run can fix a specific problem instead of regenerating blind — which is why `describeViolation` (`cms/src/components/ops/articleStatus.ts`) exists: a structural `Violation` carries the limit, the actual value, the missing tags and the offending phrase, and both the review UI and the regeneration notes used to render only its `code`. It turns each one into a plain-language `what` plus the `fix` instruction the next draft is given, and honours a legacy free-text `message` for rows written before the typed shapes. `secondaryKeywords` carries the extra searches a topic-discovery pick was grouped to cover; they reach the generate prompt and the scored query cluster, but the primary `keyword` is still what SERP research and the corpus snapshot key on. `archived` takes an article off the board **and out of every run** (`runPipeline`'s entry query filters it, not just the board view). It exists because articles cannot be deleted: `article-audit` rows are append-only (`beforeDelete` throws) and their `article_id` is NOT NULL behind an ON DELETE SET NULL foreign key, so Postgres refuses to remove an article while any audit row points at it — and every article has one from creation.
- **`CorpusSnapshots`** (`corpus-snapshots`) — the information-gain baseline captured for one `(keyword, country)` pair: the crawled SERP pages' readable text, our own related published articles, the claims extracted from both, and the consensus facets/gaps clustered from those claims. Written by the research stage with `overrideAccess: true`; read-only from the admin API otherwise. See `docs/information-gain.md`.
- **`TopicSearches`** (`topic-searches`) — cached Ahrefs keyword lookups, one row per `(seedKey, country)`, written by the discovery server action with `overrideAccess: true`. Every discovery search spends API units and the numbers barely move week to week, so a lookup is reused for 7 days (`TOPIC_SEARCH_TTL_DAYS`) and the panel offers an explicit refresh. `seedKey` is the lower-cased, whitespace-collapsed seed, so `"  NFL  Games "` and `"nfl games"` share one row.
- **`InformationGainRuns`** (`information-gain-runs`) — one immutable scoring result per draft: the full scorecard, every claim with its signals/evidence/score, the policy reasons behind the decision, the resolved policy and its `policyVersion`, and the models that judged it. `create`/`update`/`delete` are all `() => false` and a `beforeChange`/`beforeDelete` hook throws on any update or delete, so the only writer is the pipeline stage's `overrideAccess: true` create. `Article.informationGain` is a small denormalised summary pointing at the current row. See `docs/information-gain.md`.
- **`EvidenceSources`** (`evidence-sources`) — the admin's domain-quality table: one row per domain with a `qualityClass` (`first_party_dataset` | `primary` | `official_docs` | `secondary` | `unverified` | `blocked`), a `note`, and an `active` flag. Domains are normalised on save (`normaliseDomain`) and `domain` is unique. **This table is operator work, not optional setup**: an unclassified domain's source quality is capped at 0.75 (`UNKNOWN_DOMAIN_CAP`) while a materially novel factual claim needs 0.90 and a numeric one 0.95, so a novel claim cited only to unclassified domains is always blocked. `npm run seed` seeds three `primary` rows unconditionally so the mock walkthrough can pass; they are not a starter list for a real tenant. Rather than classifying domains up front, the pipeline queues the ones it actually reached for — see `EvidenceSourceCandidates` below.
- **`EvidenceSourceCandidates`** (`evidence-source-candidates`) — the review queue behind `EvidenceSources`: one row per normalised domain the informationGain stage ran into that no active rule covers, written by the stage with `overrideAccess: true` (`create/update/delete` are all `() => false`). Both the verifier's unmatched citations and the article's SERP-snapshot domains become candidates, each with a *suggested* class that can never be `first_party_dataset` or `blocked`. Worked through at `/admin/ops/governance/source-review`; `status` is the only human-owned field, and it is never the authority on whether a domain is rated — the page re-checks `evidence-sources` live, so a hand-added rule removes a candidate and a deactivated one restores it with no write. See `docs/information-gain.md`.
- **`CostLog`** — one row per LLM call (see Cost tracking above); append-only by convention — the pipeline only ever creates rows, but the collection has no access rules stopping the admin UI/API from editing or deleting them.
- **`BrandVoices`** (`brand-voices`) — the tenant's brand voice governance record (essence/mission, core values, audience, persona, three adjectives with do/don't examples, "what we are NOT" traits, four tone dials, preferred/banned words, writing samples). `status` is `draft | active | archived`; the `gateActivation` hook refuses to activate an incomplete record (`brandVoiceActivationProblems`) and `cascadeSingleActive` archives every other active record, so there is exactly one active voice at the data layer. Single-tenant today; the collection (not a Global) exists so a `tenant` relationship is a one-field addition later. Managed from the custom admin view at `/admin/ops/governance/brand-voice` (`cms/src/components/ops/BrandVoice*`), which offers an onboarding stepper or upload-and-extract (`cms/src/lib/extractText.ts` + `brandVoiceExtract.ts`).
- **`BrandVoiceFiles`** (`brand-voice-files`) — uploaded brand guides (md/txt/pdf/docx). Separate from `Media` because `Media` is publicly readable and a tenant's internal guide should not be.
- **`GovernanceAudit`** (`governance-audit`) — immutable audit rows for governance records, written by the `auditGovernanceChange` hook (`cms/src/lib/governanceAudit.ts`) with a polymorphic `subject`. In `BrandVoices` this hook must run *before* `cascadeSingleActive`: the cascade's nested update shares `req`, and Payload merges its `context` into `req.context`, so an audit hook that ran afterwards would record the wrong event.
- **`Users`** / **`Media`** — stock Payload auth/upload collections, unmodified from the Payload blank template.

Globals (`cms/src/globals/`): **Models** (`llm-settings`, see above) and **Information-gain policy** (`information-gain-policy`, `cms/src/globals/InformationGainPolicy.ts`) — the eleven scoring thresholds, every field derived from `POLICY_FIELDS` in `cms/src/lib/informationGain/policy.ts` so the global, the `INFORMATION_GAIN_*` env overrides, `DEFAULT_POLICY` and the admin copy cannot drift apart. Resolution is admin → env → default, and **no field carries a Payload `defaultValue`**: one would be persisted on the first save and become indistinguishable from a real admin choice, silently killing the env override. Both are linked from the ops nav (`ExtraOpsNavLinks.tsx`).

After changing any collection's fields, run `npm run generate:types --workspace cms` — `pipeline` imports `Article`/`Template`/`CostLog` types straight from `cms/src/payload-types.ts` via relative path (`../../cms/src/payload-types`), so stale types there will silently drift from the actual schema.

## Conventions

- CMS code: 2-space, single quotes, no semicolons, `printWidth: 100`, trailing commas (`cms/.prettierrc.json`) — run through the CMS ESLint config (`cms/eslint.config.mjs`), not a separate pipeline linter (pipeline has no lint script, only `typecheck`).
- `cms/CLAUDE.md` is `@AGENTS.md`, which is regenerated by `next dev` (Next.js 16's agent-guidance file) — don't hand-edit `cms/AGENTS.md`'s content expecting it to persist; treat it as informational, not as project-specific conventions.
- The CMS package.json's `test` script references `pnpm`, a holdover from the Payload blank template; the rest of this repo (root scripts, CI-equivalent workflows) uses npm workspaces — use `npm run test:int` / `npm run test:e2e` directly inside `cms/` rather than `pnpm test` unless pnpm is actually installed. `test:e2e` still depends on `pnpm` being installed for its `webServer` fallback (see Commands above) — that one isn't avoidable by using npm instead.
- `cms/README.md` is a short pointer back to the root README/CONTRIBUTING — the root README, `docker-compose.yml`, and `.env.example` are the source of truth for setup instructions.

## Versioning & releases

Releases are fully automated by [release-please](https://github.com/googleapis/release-please) (`.github/workflows/release-please.yml`); the process for humans is in `RELEASING.md`. The rules for agents:

- Commit messages and PR titles follow [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): subject`, e.g. `feat(cms): …`, `fix(pipeline): …`, `docs(readme): …`. PRs are squash-merged, so the **PR title becomes the commit on `main`** and is what release-please reads — CI lints it (`.github/workflows/pr-title.yml`). `fix` → patch bump, `feat` → minor, `feat!` → major. Breaking changes must carry the `!` marker in the PR title — never rely on a `BREAKING CHANGE:` footer, which the title-only squash commit drops before release-please can read it.
- The root `package.json` `version` field is the project's single version. **Never** edit it, `CHANGELOG.md`, or `.release-please-manifest.json` by hand, and never create git tags or GitHub releases manually — release-please owns all of them. The workspace `package.json` versions (`cms`, `pipeline`) are meaningless and stay untouched.
- Cutting a release = merging the open `chore(release)` PR that release-please maintains (see the `release` skill in `.claude/skills/release/`). Don't merge it as a side effect of other work — that's a human decision.
